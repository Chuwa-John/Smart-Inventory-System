## High Priority Issues

### QA-001 — Cash drawer variance is client-computed and unpinned; a cashier can zero out a short drawer

| Field | Value |
|---|---|
| **Severity** | High |
| **Priority** | High |
| **Category** | Business Logic / Financial Integrity / Insider Fraud |
| **Environment** | `firestore.rules` lines 260–274, `validShiftClose()` |
| **Confidence** | High (static analysis; not yet executed against the emulator) |

**Preconditions:** An active cashier or manager with an open shift at a store assigned to them.

**Steps to reproduce**
1. Open a shift with `openingFloat: 100000`.
2. Ring up sales totalling 500,000 in cash.
3. Remove 50,000 from the drawer.
4. Close the shift, submitting `countedCash: 550000`, `expectedCash: 550000`, `variance: 0`.

**Expected result:** The shift closes recording `expectedCash: 600000` and `variance: -50000`, surfacing the shortfall.

**Actual result:** The write is accepted. `validShiftClose()` pins `openingFloat`, `openedByUid`, `openedAt` and `storeId` against the opening document, but `expectedCash` is only checked with `moneyInRange()` — any value from 0 to 1,000,000,000 is accepted. `variance` is likewise only range-checked, and is never cross-checked against `countedCash − expectedCash`.

**Possible root cause:** The rule's own comment identifies precisely this attack via a different field — *"Without pinning the opening fields, a short drawer could be reconciled away after the fact by raising the float it claims to have started with."* The opening float was pinned; `expectedCash`, which is the other operand in the same subtraction, was not. It cannot be pinned the same way because Firestore rules cannot aggregate the shift's sales to derive it.

**Business impact:** Shift reconciliation is the primary control over physical cash. If the cashier supplies both sides of the variance calculation, the control reports what the cashier chooses rather than what happened. Cash shrinkage becomes invisible in exactly the workflow built to expose it. For a supermarket operator with rotating branch staff — a threat model this project explicitly designs around — this is the highest-value finding in the report.

**Recommended fix (in preference order)**
1. **Server-side derivation.** Compute `expectedCash` in the proxy from the shift's own sales and write the closing document with the Admin SDK. Rules then pin it the way `openingFloat` is pinned. This is the only option that actually closes the gap.
2. **Minimum viable hardening in rules.** Enforce internal consistency — `variance == countedCash − expectedCash` — so the three numbers must at least agree with each other. This does not stop a fabricated `expectedCash`, but it removes the trivial case of submitting an inconsistent triple, and costs one expression.
3. **Detective control.** Add an owner-facing report comparing each closed shift's recorded `expectedCash` against the sum of that shift's cash sales, flagging any divergence. Cheap, and catches the attack after the fact.

At minimum, if none of these ship before release, record this in a Known Limitations document with the compensating control named — the same treatment F-4 already receives in `SECURITY-AUDIT.md`.

### QA-002 — `auditLogs` entries are unvalidated; a cashier can forge action strings and flood the collection

| Field | Value |
|---|---|
| **Severity** | High |
| **Priority** | High |
| **Category** | Security / Audit Integrity / Broken Access Control |
| **Environment** | `firestore.rules` lines 283–286 (`validAuditLog()`) and 567–577 |
| **Confidence** | High |

**Steps to reproduce**
1. Authenticate as a cashier.
2. Write to `users/{ownerUid}/auditLogs/{any}` with `{ uid: <own uid>, action: "SALE_VOIDED", ...arbitrary fields of arbitrary size }`.
3. Repeat in a loop.

**Expected result:** Rejected, or accepted only with a bounded, enumerated `action` and bounded payload.

**Actual result:** Accepted. `validAuditLog()` checks only that `uid == request.auth.uid` and `action is string`. There is no enum on `action`, no length bound on it, no bound on any other field, and no cap on document size or write rate.

Three consequences follow:

- **Forgery of meaning.** A cashier can write `action: "SALE_VOIDED"` or `"CREDIT_LIMIT_CHANGED"` referencing sales they never touched. The `uid` field is honest, but everything the owner actually reads is attacker-controlled.
- **Log flooding.** Unbounded document size and unbounded write rate mean the collection can be filled with noise to bury a genuine entry. `auditLogs` has no rate limiting at the rules layer.
- **Cost amplification.** Firestore bills per write and per stored byte, against the owner's account, driven entirely by a staff member's client.

**Contrast within the same file:** `errorLog` (lines 549–565) — a strictly *less* security-critical collection — is carefully bounded: `message` ≤ 300 chars, `kind` restricted to an enum, `where` ≤ 200, `appVersion` ≤ 40. `auditLogs` receives none of this.

**Business impact:** `SECURITY-AUDIT.md` F-4 and `tests/README.md` both name the audit log as *the* compensating control for the one thing rules provably cannot enforce (binding a stock decrement to a sale). `SECURITY-AUDIT.md` marks audit trails PARTIAL, but the gap it records is *"the project owner has full console access and could delete entries out-of-band"* — an owner-side risk. The staff-side risk documented here is not recorded anywhere. The control that the security model leans on hardest is the least validated collection in the schema.

**Recommended fix:** Mirror the `errorLog` treatment. Constrain `action` to the ten values `app.js` actually writes (`SALE_COMPLETED`, `SALE_VOIDED`, `RETURN_PROCESSED`, `PAYMENT_RECORDED`, `CREDIT_LIMIT_CHANGED`, `CREDIT_LIMIT_EXCEEDED`, `PRODUCT_RESTOCKED`, `PRODUCT_DELETED`, `STORE_CURRENCY_CHANGED`, `STORE_ARCHIVED`), bound every string field, and reject unexpected keys with `hasOnly()`. Rate limiting needs a different layer — note it rather than attempt it in rules.

**Regression risk of the fix:** Moderate and easily contained. Any `action` value written by `app.js` but omitted from the enum will start failing silently at the till. Enumerate from the grep of `app.js` (all ten are listed above), and add a test asserting every constant in the client appears in the rule.

## Medium Issues

### QA-003 — Service worker pre-caches `./app.js` but the app requests `./app.js?v=...`

| Field | Value |
|---|---|
| **Severity** | Medium |
| **Priority** | Medium |
| **Category** | Performance / Caching / Cost |
| **Environment** | `sw.js` line 13 (`APP_SHELL`), `app.html` line 987 |
| **Confidence** | High |

**Actual result:** `APP_SHELL` lists `"./app.js"` with no query string. `app.html` requests `"./app.js?v=20260802l"`. Cache keys include the query string, so these are two different entries. On every service-worker install the browser downloads 406 KB of `app.js` under a key that is never read, then downloads it a second time under the versioned key via the runtime cache-first branch.

Both sibling assets are handled correctly — `styles.css?v=20260802l` and `boot.js?v=20260802l` appear in `APP_SHELL` with matching versions — which is what identifies this as an oversight rather than a deliberate choice.

**Business impact:** ~406 KB of wasted transfer per device per deploy. On the metered mobile connections this product targets, and with `CACHE_NAME` currently at v72, that is not trivial. Correctness is unaffected: the versioned URL still resolves via runtime caching, and version bumping still busts the cache properly.

**Recommended fix:** Change the `APP_SHELL` entry to `"./app.js?v=20260802l"`. Then add a test asserting every versioned asset reference in `app.html` and `accept-invite.html` appears verbatim in `APP_SHELL` — this class of drift will otherwise recur on every version bump, silently.

**Note:** All eleven `APP_SHELL` entries were verified to exist on disk. This matters because `cache.addAll()` is atomic — one missing file rejects the whole install and silently disables offline mode. Worth an automated existence check for the same reason.

### QA-004 — Any store-scoped staff member can close another staff member's open shift

| Field | Value |
|---|---|
| **Severity** | Medium |
| **Priority** | Low |
| **Category** | Business Logic / Authorization |
| **Environment** | `firestore.rules` lines 498–514 |
| **Confidence** | Medium |

`validShiftClose()` requires `closedByUid == request.auth.uid` — the closer cannot impersonate someone else, which is correct. But nothing requires the closer to be the person who opened the shift, or to hold a supervisory role. Any cashier assigned to that store can close a colleague's drawer and submit the count for it.

This may well be intentional — a manager closing out for a cashier who has left for the day is normal retail practice, and the closing identity is recorded. Flagged for a product decision rather than as a defect. If unintended, the fix is to require `closedByUid == resource.data.openedByUid || memberRole(userId) == "manager"`.

**Interaction with QA-001:** if a cashier can both close someone else's shift *and* supply the expected figure, the attribution trail for a shortfall becomes ambiguous. Worth resolving alongside QA-001 rather than separately.

## Security Findings

Strong, with two exceptions already recorded above (QA-001, QA-002).

Verified correct by inspection:

- **Multi-tenancy isolation.** Every collection is nested under `users/{ownerUid}`, and every staff branch resolves role and store access through `get()` on `members/{staffUid}` rather than a custom claim. Revocation is therefore effective on the next request rather than at token expiry. The single custom claim in use (`businessOwnerUid`) is a routing hint and is never consulted for authorization — confirmed at `app.js:6240` and in `proxy/server.js`.
- **Privilege escalation via `members`.** `allow write: if isOwner(userId)` — a staff member cannot write their own member document, so cannot self-promote. Self-*read* is permitted (needed for UI role resolution) and correctly scoped to `request.auth.uid == staffUid`.
- **Override-password handling.** `private/security` is `allow read, write: if false` for all clients including the owner, with the reasoning recorded inline: a readable hash could be brute-forced offline. Both proxy endpoints derive the tenant from the verified token claim (`getBusinessOwnerUid`, `server.js:316`), and the setter additionally rejects when `req.user.uid !== businessOwnerUid` — so staff may verify against the password but never set it. The scoping bug described in the project handoff is fixed in the current code.
- **Numeric bounds.** `countInRange` / `moneyInRange` / `totalInRange` close the `Infinity`-and-beyond-2^53 hole, with the reasoning and the measurement recorded. `signedMoneyInRange` correctly exists so that a *negative* variance — the case worth reading — is not rejected by the unsigned helpers.
- **Append-only enforcement.** `sales`, `auditLogs`, `errorLog`, `transfers`, `payments` and `shifts` all forbid delete; `auditLogs`, `errorLog`, `transfers` and `payments` also forbid update.

**Not assessed this pass:** JWT validation depth, CSRF, rate-limiting effectiveness under load, dependency CVEs, session expiry behaviour. `SECURITY-AUDIT.md` covers several of these; I did not independently verify its claims.

## Performance Findings

1. **Rule evaluation cost per staff write.** `isOwnerOrRole()` and `memberCanAccessStore()` each resolve through `isActiveMember()`, which performs an `exists()` plus a `get()`, followed by a further `get()`. A single staff write can therefore issue several document accesses before the write itself. Firestore caches identical `get()` calls within one evaluation, so the practical cost is lower than the textual count, but it is non-zero and billed — and an owner short-circuits past all of it at `isOwner()`, so staff-heavy traffic costs measurably more than owner traffic. `tests/rules-budget-probe*.mjs` already measures the 1000-expression ceiling; extending it to count billed reads per write would make this visible.
2. **`payments` requires a parent-document `get()`** on every read and create (lines 482, 485) to resolve the customer's `storeId`. Denormalising `storeId` onto the payment document would remove one billed read per payment operation.
3. **QA-003** — 406 KB of redundant transfer per device per deploy.

**Not assessed:** page load, render performance, search at scale, large-dataset behaviour, memory over time. `SECURITY-AUDIT.md` marks load/stress/chaos as a GAP, which matches what I can see.
